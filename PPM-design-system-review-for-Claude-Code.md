## 3. Загальний висновок

Зберегти візуальний напрям. Система добре відповідає предметній області PMO: звіти, ризики, погодження, команди, аналітика. Є світла й темна теми, предметні компоненти, правила текстів та суттєва мобільна адаптація.

Основні проблеми: читабельність і доступність, неповний контракт поведінки компонентів, ризик розходження каталогу та продукту, ручна синхронізація токенів, помилки експортованих артефактів. Повна заміна дизайну або UI-фреймворку не обґрунтована.

Авторство Claude Code не доводить наявність дефекту. Додаткові рекомендації нижче стосуються перевірюваності результату, а не оцінки інструмента чи автора.

## 4. Пріоритети та статуси доказів

- **P0:** усунути до заяви про готовність відповідного основного сценарію до доступного мобільного використання.
- **P1:** суттєве покращення зручності або надійності, планувати найближчим етапом.
- **P2:** розвиток після стабілізації основних сценаріїв.
- **Факт архіву:** безпосередньо підтверджено наданими файлами; застосовність до production ще перевіряється.
- **Ризик:** є підстава для перевірки, але дефект продукту не доведений.
- **Пропозиція:** потребує продуктового рішення або перевірки з користувачами.

## 5. Реєстр помилок і перевірок

### DS-01. Недостатній контраст тексту — P0, факт архіву

Джерела: `tokens.css`, `components/bundle.css`, `review.md`.

| Поєднання | Світла тема | Темна тема |
|---|---:|---:|

| Білий на `theme-2` | 5,80:1 | 2,83:1 |

Вплив: дрібні цифри графіків, оцінки ризику, кнопки та підписи можуть бути важкими для читання. Hover головної кнопки в темній темі потенційно погіршує контраст.

Рекомендація: розділити семантичні ролі `action-primary-bg`, `action-primary-fg`, `link-fg`, `focus-ring`, `status-*-fg/bg`. Назви орієнтовні; зберегти сумісність через aliases за потреби. Колір статусу не повинен автоматично бути фоном для білого тексту.

Критерій: звичайний інформаційний текст має щонайменше 4,5:1; великий текст — 3:1; перевірені всі фактично використані фони й інтерактивні стани обох тем. Недоступні контролі та декоративні елементи оцінювати з урахуванням винятків стандарту.

Не застосовувати `text` як універсальний темний foreground: у темній темі цей токен світлий.

### DS-02. Неточні рекомендації WCAG у review.md — P1, факт архіву

У документі запропоновано 17 px bold як можливий вихід для слабкого контрасту та поставлено питання про допустимість 12 px bold на червоному. Обидва розміри потребують 4,5:1. Поріг великого жирного тексту — 14 pt, приблизно 18,67 CSS px; звичайного — 18 pt, тобто 24 CSS px.

Другорядний або «необов’язковий» зміст не стає суто декоративним. Підписи KPI й осей мають інформаційну функцію.

Критерій: документація не містить цих поблажок; автоматичні перевірки спираються на реальні розмір, вагу шрифту, foreground і background.

### DS-03. Слабко видимий фокус — P0, факт архіву

Джерела: `components/bundle.css:89`, правила radio/scale та `tokens.css`.

Фокус `3px solid var(--theme-soft)` на `bg` дає приблизно 1,17:1 у світлій і 1,28:1 у темній темі. Товщина не компенсує слабку відмінність кольорів.

Рекомендація: окремий непрозорий токен фокуса, перевірений на сусідніх поверхнях; перевірка обрізання outline контейнерами. Не видаляти стандартний outline без достатньої заміни.

Критерій: фокус видно на всьому маршруті Tab / Shift+Tab, він не перекритий sticky-панелями; забезпечений необхідний non-text contrast там, де застосовний SC 1.4.11. Не видавати вимоги AAA Focus Appearance за вимоги AA.

### DS-04. Мобільна навігація втрачає доступні назви — P0, факт прикладу

Джерела: `components/Nav/preview.html`, `components/bundle.css:218`.

До 720 px `.nav .nl` приховано через `display:none`; кнопки розділів у прикладі не мають окремого `aria-label`, SVG мають `aria-hidden=true`.

Рекомендація: перевірити accessible name реальних кнопок у мобільному DOM; додати стабільні назви. Видимі короткі підписи бажані також для зрячих користувачів. Для другорядних розділів розглянути «Ще», якщо меню не вміщується.

Критерій: кожна кнопка має змістовну локалізовану назву й оголошення поточного розділу; основні розділи розпізнаються без наведення мишею.

### DS-05. Матриця станів залежить лише від кольору — P0, факт прикладу

Джерело: `components/StateMatrix/preview.html`; також перевірити `.ragdot`, `.dims4`, графіки.

Клітинки містять кольорові крапки без текстового еквівалента. Додати видимий символ/скорочення та доступну назву; стан «не оцінено» має бути окремим зрозумілим станом. Не покладатися лише на hover tooltip.

Критерій: стан, дата й вимір зрозумілі без кольору та через скринридер. Для графіків забезпечено текстовий підсумок або доступне табличне представлення даних.

### DS-06. Неповна доступна поведінка в прикладах — P0 для ключових сценаріїв, факт прикладів / ризик продукту

| FormField | Є aria-invalid; немає зв’язку тексту помилки з полем | Унікальний id помилки, aria-describedby, перехід до першої помилки |

### DS-07. Неоднакові сенсорні цілі — P1, факт CSS

Джерело: `components/bundle.css`, блоки `@media (pointer: coarse)`.

Основні кнопки мають min-height 44 px; segmented buttons — 36 px; закриття — 40×40 px; фільтри таблиці — 28×28 px; `.date-native` — 32×32 px. Самої висоти недостатньо: перевіряти повну активну область.

Рекомендація для вебпродукту: комфортні 44–48 CSS px для основних сенсорних дій, без перекриття сусідніх цілей. Видимий значок може лишатися меншим.

Уточнення: WCAG 2.2 AA SC 2.5.8 — 24×24 CSS px із винятками; Android native guidance — 48×48 dp. Це різні вимоги й одиниці, не автоматична підстава оголосити всі 28 px кнопки порушенням WCAG.

### DS-08. Мобільні картки та середні ширини — P1, факт механізму / ризик покриття

Джерела: `components/bundle.css:2933`, DataTable, MobileCards.

За ширини до 600 px приховується лише `.tablewrap.dt.has-cards`. Перевірити, які production-списки справді мають картки й прапорець. Не дублювати прихований набір даних у accessibility tree.

Для 600–1100 px визначити поведінку колонок: ключові поля, розкриття деталей, горизонтальний скрол у контейнері. Не вважати `overflow-x:clip` доказом відсутності проблем: він може приховати недоступний контент.

Критерій: немає обрізаних основних дій; фільтри й сортування доступні в обох представленнях; дійсно двовимірні таблиці можуть мати власний горизонтальний скрол.

### DS-09. Ширина вебчастини й оточення SharePoint — P1, ризик

CSS переважно використовує viewport media queries. У SPFx доступна ширина вебчастини залежить також від колонки сторінки та панелі властивостей.

Рекомендація: оцінити container queries або підтримувані `width` / `onAfterResize`. Не переписувати всі breakpoint-и без перевірки реального способу розміщення порталу.

Окремо перевірити `.pmo-app.pmo-sp .pmo-panel/.pmo-scrim { top:48px }`, sticky-offset-и, safe area, клавіатуру, landscape, браузерні панелі та Teams. Фіксовані 48 px не вважати універсальною властивістю всіх host-контекстів.

### DS-10. Помилка генерації tokens.css — P1, факт архіву

Джерело: `tokens.css:158` і наступні типографічні правила.

15 правил закінчуються `}}`; закривальних дужок на 15 більше, ніж відкривальних. Приклад: `.page-title { ... letter-spacing: -0.025em; }}`.

Рекомендація: знайти генератор, виправити джерело помилки, повторно згенерувати всі похідні артефакти, включно з вбудованими стилями каталогу. Не обмежуватися ручною правкою експорту.

Критерій: CSS проходить синтаксичну перевірку; браузер отримує очікувані типографічні правила. Сам факт browser error recovery не означає коректності файлу.

### DS-11. Контракт теми потребує уточнення — P1, частково уточнений висновок

Джерела: HANDOFF, початок і кінець `components/bundle.css`, `tokens.css`.

HANDOFF рекомендує data-theme на html. Частина правил color-scheme перевіряє атрибут на самій `.pmo-app`. Водночас у кінці bundle.css є `[data-theme="dark"] .pmo-app { color-scheme:dark }` — воно покриває explicit dark на предку.

Тому твердження «темна тема на html завжди не працює» було б неправильним. Конкретний ризик: за системної dark і explicit light на html правило `.pmo-app:not([data-theme=light])` усе ще може встановити dark color-scheme для нативних контролів, якщо атрибут не продубльовано на корені застосунку.

Критерій: перевірити всі 6 комбінацій system light/dark × вибір system/light/dark. Палітра, нативні select/date/input і фактичне значення color-scheme мають відповідати вибору.

### DS-12. Демонстраційні й глобальні стилі в reusable bundle — P1, факт архіву / ризик інтеграції

У кінці `components/bundle.css` є `html,body{margin:0;background:var(--bg-page)}` та `.ds ...` overrides, які роблять панелі й тости статичними. У `tokens.css` є глобальні `.body`, `.table`, `.label`, `.pill` та :root-токени. HANDOFF водночас пропонує використовувати bundle у вебпроєкті.

Рекомендація: розділити production component CSS і catalog-only CSS; ізолювати стилі та токени PPM від SharePoint і сусідніх вебчастин. Врахувати портали/popover-и, які можуть монтуватися поза коренем.

Критерій: підключення компонентної бібліотеки не змінює body, host-тему й сторонні компоненти; demo overrides відсутні в production bundle.

### DS-13. Ручна синхронізація токенів і неповне застосування шкал — P1, факт процесу

Джерела: workflow.md, tokens.css, bundle.css.

Документовано ручне перенесення tokens.json у SCSS. У компонентних стилях багато числових font-size, padding і radius. Наявність токена не означає, що зміна токена вплине на всі компоненти.

Рекомендація: визначити єдине канонічне джерело та автоматичну генерацію CSS/SCSS і документації. Медіазапити не переписувати як `@media(max-width:var(--bp-...))`: звичайні CSS custom properties не працюють там як runtime breakpoint-и; потрібна build-time підстановка або інша стратегія.

Критерій: контрольна зміна токена доходить до реального компонента та каталогу; повторна генерація без зміни входу не створює diff; допустимі локальні значення документовані.

### DS-14. Заявлена DTCG-сумісність не підтверджена — P1, факт формату / ризик імпорту

У tokens.dtcg.json значення color записані рядками hex/rgba. Формат DTCG 2025.10 описує структуровані кольори з colorSpace/components і alpha за потреби.

Рекомендація: вказати цільову версію формату; перевірити всі типи токенів; виконати імпорт і зворотний експорт у реально обраній версії інструмента. Наявність $type/$value недостатня для заяви про повну сумісність. Конкретний інструмент може підтримувати legacy-формати — це треба перевірити, а не припускати.

Критерій: обидві теми, прозорість, розміри, тіні й типографіка імпортуються без втрати значень. DTCG Community Group specification не називати W3C Recommendation.

### DS-15. Неповні стани операцій — P1, прогалина специфікації / ризик продукту

review.md вказує відсутність окремого loading-стану кнопки подання. Водночас у CSS є loading-анімації та refresh-btn[aria-busy]; не стверджувати, що loading відсутній у всій системі.

Перевірити саме операцію подання звіту: pending, success, validation error, network failure, permission failure, конфлікт одночасного редагування, повторне натискання.

Рекомендація: явний статус «Подання…», збереження введеного при помилці, зрозумілий retry; захист від дублювання має враховувати також повторний запит, а не тільки disabled-кнопку. Якщо вже є version/ETag-механізм, перевірити його використання.

Критерій: подвійний клік не створює два звіти; невдала операція не виглядає успішною; користувач не втрачає введені дані.

| UX-01 | Рольова головна: PM — мої звіти; PMO — погодження; керівник — рішення й відхилення | Порівняти час до першої потрібної дії |
| UX-02 | Послідовні назви «Фаза проєкту», «Стан проєкту», «Статус звіту» | Перевірити розуміння новими користувачами |
| UX-03 | Пояснення RAG: за планом / потребує уваги / критичне відхилення | Узгодити правила з PMO; не перейменовувати збережені значення без аналізу |
| UX-04 | Компактний і комфортний режими таблиці; персональні фільтри й колонки | Перевірити щоденні сценарії PMO та мобільні задачі |
| UX-05 | Видимий стан чернетки та захист незбережених змін | Перевірити Esc, backdrop, «Назад», закриття вкладки; вибрати політику чернеток |
| UX-06 | Empty states за причиною: немає проєктів / фільтр нічого не знайшов / немає доступу / помилка | Для кожного стану дати доречну наступну дію |
| UX-07 | Прямі посилання на проєкт/звіт, передбачувана browser history | Перевірити відкриття посилання й повернення до фільтрованого списку |
| UX-08 | Прозорий ШІ: використані дані, пропозиція змін, прийняти/відхилити | Перевірити, чи людина розрізняє рекомендацію та вже збережену зміну |

Додаткові кольори для кожної фази не обов’язкові: надлишок кольорових значень може погіршити сканування. Ілюстрації, новий логотип і косметична уніфікація радіусів мають нижчий пріоритет за читабельність і успішність операцій.

## 7. Особливі рекомендації для роботи Claude Code

### 7.1. Спочатку відновити походження артефактів

Побудувати коротку карту: prototype → extract-prototype.mjs → prototype.scss/overrides → React application → export/catalog. Перевірити фактичний напрям генерації й відмінності від workflow.md. Знайти, що генерує tokens.css і tokens.dtcg.json.

Не редагувати одночасно всі копії навмання. Зміни робити у встановленому канонічному джерелі та регенерувати похідні файли.

### 7.2. Не плутати покриття класів із покриттям поведінки

Заявлені «313 із 331 класів» показують представленість CSS-класів. Вони не доводять доступності, функціональної повноти чи мобільної готовності.

Потрібна матриця: компонент × стан × тема × спосіб вводу × потрібний сценарій. Не вимагати повного декартового добутку для всіх дрібних компонентів; застосувати ризик-орієнтований відбір.

### 7.3. Не переписувати весь стек

Зчитати package.json і lockfile; визначити SPFx, React, TypeScript, Fluent UI/PnP та build toolchain. Версії підбирати за матрицею сумісності SPFx. Не встановлювати «latest» як автоматичне покращення.

Для складних accessible primitives оцінити сумісний Fluent UI/PnP або наявну перевірену реалізацію. Використання бібліотеки не замінює перевірки композиції та поведінки.

### 7.4. Перевіряти артефакти незалежним способом

- CSS — парсер/лінтер, а не лише факт успішної генерації.
- Контраст — розрахунок із реальних computed styles і compositing там, де є прозорість.
- Accessible name — accessibility tree, а не пошук aria-label у тексті.
- Адаптивність — rendered layout і досяжність дій, а не лише наявність @media.
- DTCG — валідатор і тест імпорту обраного інструмента.
- Сценарії — взаємодія з реальними production-компонентами; статичні preview не замінюють їх.

### 7.5. Малими завершеними змінами

Після окремого погодження реалізації: спершу дефекти експорту та критична доступність, потім мобільні сценарії, далі автоматизація й продуктова перебудова. Кожна зміна повинна мати конкретний trigger, before/after і релевантну перевірку. Не створювати тести, які лише повторюють implementation details.

Не проводити міграції українських значень SharePoint під виглядом редагування підписів. Не змінювати дозволи й бізнес-правила погодження заради спрощення UI.

## 8. Матриця приймання

| Вимір | Мінімальне покриття |
|---|---|
| Ширина | 320, 375/390, 600, 720/768, 920, 1100, 1440 CSS px; вузька вебчастина в широкому viewport |
| Breakpoint boundaries | По обидва боки змінених порогів, зокрема 600/601 і 720/721 |
| Теми | System light/dark × system/light/dark override |
| Мови | uk/en/ru; довгі назви, великі суми, відсутні значення |
| Браузери/host | Підтримувані desktop-браузери, Safari iOS, Chrome Android; Teams лише якщо входить у scope запуску |
| Ввід | Миша, клавіатура, touch; телефон із відкритою клавіатурою; portrait/landscape |
| Accessibility | Автоматична перевірка плюс ручні keyboard/VoiceOver/TalkBack; релевантний desktop screen reader |
| Масштаб | Текст 200%; reflow до еквівалента 320 CSS px, без втрати основних дій |
| Дані | Порожньо, типовий набір, великий реалістичний набір, помилки запитів і конфлікти |

Обов’язкові сценарії:

1. PM знаходить свій проєкт, створює чернетку, виправляє помилку та подає звіт.
2. PMO знаходить звіт і повертає його з причиною або погоджує.
3. Керівник знаходить критичний ризик і розуміє, яке рішення потрібне.
4. Після помилки мережі введені дані лишаються доступними; повторна дія не створює дубль.
5. Після закриття панелі відновлюються логічний фокус, позиція й контекст списку.

Автоматичні accessibility-перевірки не доводять повної відповідності WCAG. Поведінку клавіатури, зміст і зручність перевіряти окремо. Для користувацького тестування залучити представників PM, PMO й керівників; фіксувати успішність, час, помилки та потребу в допомозі.

## 9. Що саме означає мобільний запуск

Дизайн-система придатна як основа responsive web для Android/iPhone. Архів не доводить готовності нативного застосунку, PWA/offline або дистрибуції через магазини.

У плані явно зафіксувати ціль: мобільний браузер, Teams/інший host або окремий застосунок. З огляду на наданий контекст базове припущення — responsive SharePoint/SPFx portal. Не додавати native wrapper чи service worker без окремої потреби та перевірки платформи.

## 10. Очікуваний результат аналізу Claude Code

Повернути:

1. Стислий висновок: що підтверджено, що спростовано, що вже виправлено.
2. Таблицю за всіма DS-ID: статус, актуальний файл/символ, вплив, пріоритет, рекомендована зміна, перевірка.
3. Окремий список продуктових рішень UX-ID, які потребують вибору замовника.
4. План невеликих етапів із залежностями та ризиками; оцінки трудомісткості — діапазонами після огляду коду.
5. Перелік фактично виконаних команд/тестів та неперевірених сценаріїв.
6. Пропозицію першого конкретного пакета виправлень для подальшої реалізації.

За браку доступу до живого SharePoint виконати доступний аналіз репозиторію; чітко зазначити, що саме залишається неперевіреним. Не підміняти відсутність доступу припущенням про успішний запуск.
