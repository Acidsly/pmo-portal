# Защита от «окон» и устаревших страниц + отзывы раунда 2 — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** закрыть все сценарии, в которых устаревшая страница, окно до синхронизации или прямой запрос к SharePoint портит проекты, отчёты, риски, команду и права; внести принятые отзывы Дениса (#23–#33) без замедления приложения и синхронизации.

**Architecture:** три уровня. (C) права SharePoint: участники сайта — только чтение дочерних списков, записи создаются сразу в папке проекта, у отчётов, комментариев и погоджень — роль «только добавление»; эталон ключевых полей в закрытом списке `ProjectState`. (B) синхронизация — единственный источник правды: применяет отчёт только по решению PMO из `ReportApprovals`, откатывает ключевые поля к эталону, один отчёт на погодженні на проект, автоматический возврат отчётов при смене PM и архиве. (A) приложение: свежая проверка перед каждой записью, ETag, лёгкая проверка изменений, понятные сообщения.

**Tech Stack:** SPFx 1.23.2 (React 17, TypeScript, Jest), PnP.PowerShell 3 / CSOM, pwsh 7.6, SharePoint REST (`AddValidateUpdateItemUsingPath`, `If-Match`).

**Spec:** этот документ + `docs/SPEC.md` (обновляется в этапе 9). Решения пользователя 30.09.2026 — раздел «Решения».

## Global Constraints

- Ключевые показатели (статус, состояние, тип, %, даты, затраты, архив) меняются **только** погодженим статус-отчётом — никаких исключений (решение п. 2).
- Приложение SPFx не пишет ключевые показатели, журнал, права, `pmoAcl`, `pmAccess`, `ProjectState`.
- Внутренние имена полей не переименовываются; значения выбора — на украинском, переводы — `i18n/values.ts` и `VAL` прототипа.
- Данные не теряются: никаких удалений списков и элементов; миграции — блоком в `Deploy-PMO.ps1`, идемпотентно.
- Фильтры REST по большим спискам — только по индексированным полям.
- PowerShell: имена переменных без коллизий по регистру (`Test-Scripts.ps1`).
- Скорость: обычный запуск синхронизации ≤ 30 с в тихие часы (сейчас медиана 26 с); полный пересчёт прав ≤ 3 мин (сейчас 2,5 мин); загрузка данных приложения не дольше текущей (+≤ 50 мс); сохранение +≤ 250 мс.
- Прод — только после отдельного «да». Push / merge — только после «да».
- Правила, которые есть и в синхронизации, и в приложении, — общими векторами `tests/cases/*.json`.

## Решения пользователя (30.09.2026)

1. Уровень C (права SharePoint) — делаем; окно до 15 мин для нового проекта допустимо.
2. Эталон `ProjectState` — делаем; правило «ключевые — только отчётом» не нарушается.
3. Один отчёт «на погодженні» **на проект** (не на PM).
4. При смене PM отчёты старого PM «на погодженні» возвращаются автоматически с комментарием.
6. Архив — только просмотр для всех, **комментарии в архиве запрещены** (права папки + интерфейс: форма комментария в архивной карточке скрыта; `guard('comment')` → `gArchived`). Уже написанные комментарии остаются видны.

# комментарии — всем, кто видит активный проект, «только добавление»; архив — только чтение всем (решение 30.09);
# журнал и погодження — чтение; риски и команда — PM правит. Векторы tests/cases/folders.json.
function Get-FolderRole([string]$list, [string]$level, [bool]$archived) {
    if ($archived) { return "read" }

        "Lists/ProjectComments" { return "add" }
        "Lists/StatusReports"   { if ($level -eq "edit") { return "add" } return "read" }

        default { if ($level -eq "edit") { return "edit" } return "read" }
    }
}

function Get-GroupFolderRole([string]$list, [bool]$archived) { if (-not $archived -and $list -in @("Lists/ReportApprovals", "Lists/ProjectComments")) { return "add" } return "read" }
