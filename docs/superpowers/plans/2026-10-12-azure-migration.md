# Переезд PPM в Azure: Azure SQL + Azure Functions — план

Версия 2, 12.10.2026 (после кросс-ревью Sonnet). Статус: **черновик для решения**; реализация — после подтверждения PMO (письмо от 12.10, срок 14.10), согласования с ИБ и вашего «да».

## 1. Коротко

- **Сейчас:** данные — 12 списков SharePoint; приложение SPFx читает и пишет их напрямую; правила, права, журнал и сповіщення — синхронизация PowerShell в Azure Automation раз в 15 минут; права — на записях и папках SharePoint; «эталон» откатывает ключевые поля, изменённые в обход отчёта.
- **Станет:** данные — **Azure SQL Database**; логика и проверки — **Azure Functions** (API + задания по таймеру); приложение SPFx (и позже Teams) ходит только в API под учётной записью пользователя (Entra ID). SharePoint — «хост» страницы Portal.
- **Выигрываем:**
  - правила выполняются **сразу и в одной транзакции**: погодження — сразу карточка, журнал, архив, сповіщення;
  - отпадают обходные механизмы: эталон, `pmEditLog`, `srApplied`, папки `P<ID>`, права на каждую запись, лимиты REST;
  - один API для портала, Teams и Copilot (блоки 4–5); Power BI — к SQL.
- **Меняется:** данные выходят из-под политик Microsoft 365 (хранение, eDiscovery) — нужно согласование с ИБ; появляется ежемесячная плата и своя ответственность за бэкапы (разделы 10, 11).
- **Объём:** на тесте — сотни записей (журнал ~200); на проде за год — тысячи; база < 100 МБ на годы. Нагрузка и стоимость минимальные.

## 2. Главное решение: порядок с переходом на прод (блок 3)

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Прод на SharePoint сейчас, Azure потом** | Блок 3 сразу после подтверждения PMO; переезд — следом, с теневым периодом | Компания работает через ~1 неделю | Перенос живых данных прода с окном обслуживания; две схемы какое-то время |

## 3. Целевая архитектура

```
Пользователь (браузер / Teams)
   │  страница Portal на SharePoint (SPFx) — интерфейс
   │  токен Entra ID v2 для «PPM API» (AadHttpClient)
   ▼
Azure Functions «ppm-api» (Flex Consumption, Node.js 22 LTS, TypeScript)
   ├─ HTTP API: данные портала, формы, погодження, призначення, коментарі, сповіщення, відгуки, поиск людей
   ├─ таймеры (каждые 15 мин / час / неделю): оргструктура и права, напоминания PM, участники сайта, экспорт бэкапа
   └─ правила — общий пакет packages/ppm-logic (вынесен из spfx/.../logic), те же векторы tests/cases/*.json
   │  управляемая идентичность — без паролей и строк подключения с секретом
   ▼
Azure SQL Database «ppm» (вход только Entra ID) ── представления только для чтения → Power BI
Azure Storage: скриншоты отзывов, экспорт бэкапов, служебное хранилище Functions (вход по идентичности)
Application Insights + Log Analytics: журналы, оповещения
Microsoft Graph (приложение, только чтение): пользователи, руководители, должности
```

- **Регион:** Germany West Central — как у текущего Azure Automation; там же Application Insights и Log Analytics.
- **Почему TypeScript:** правила уже на TypeScript в `spfx/.../logic/` и проверены общими векторами; выносим их в пакет `packages/ppm-logic`, который собирают и SPFx, и API. Логика `Invoke-PMOSync.ps1`, которой нет в `logic/`, переносится с теми же векторами (реестр — раздел 7.3).
- **Flex Consumption:** оплата за выполнение, бесплатный месячный объём, VNet и управляемая идентичность; холодный старт Node — секунды; при необходимости — «всегда готовый» экземпляр. Особенности: нет слотов развёртывания и Kudu, публикация — через контейнер хранилища; доступность в регионе и Node 22 подтвердить при заказе.
- **Teams и Copilot (блоки 4–5)** — к тому же API (раздел 5.6).

## 4. Модель данных в SQL

| Таблица | Из списка | Что меняется |
|---|---|---|
| `Project` | Проєкти | ключевые показатели — только процедурой погодження (раздел 5.5); убираются `pmoAcl`, `pmAccess`, `pmEditLog`, `pmMigrated`, `pmLoop`; `rowversion` |
| `ProjectLink`, `ProjectTeam` | `pmLinks` (JSON), Команда проєкту | отдельные таблицы |
| `StatusReport`, `ReportApproval`, `Assignment` | одноимённые | погодження и призначення — транзакцией; флаги `srApplied` / `apApplied` / `paApplied` не нужны |
| `RiskIssue` | Ризики та проблеми | `riScore` — вычисляемый сохраняемый столбец |
| `Comment`, `ChangeLog` | Коментарі, Зміни показників | пишет только API; `teamIn` / `teamRole` — отдельные столбцы |
| `NotifyRead` | Прочитане | метки `ReadId` / `ReadCmId` и ключи прочитанного |
| `Feedback`, `FeedbackFile` | Відгуки (+ вложения) | файлы — в Storage; общий список не нужен |
| `ProjectAccess` | (права на записи) | вычисленный доступ проект × пользователь × роль — правило `Get-Access` / `logic/access.ts` |
| `Person` | (пользователи сайта) | ключ — e-mail (нормализованный) + Entra object id; имя, должность, руководитель, активен ли; уволенные остаются (история не рвётся) |
| `Setting`, `SchemaVersion` | — | служебные |

- **Даты «только дата»** — тип `date`; импорт применяет правило `DateOnly` (полдень UTC и полночь по поясу сайта); API отдаёт `YYYY-MM-DD`. Разбор региональных форматов (`formValues`) в приложении уходит. Векторы на «сдвиг на день».
- **Системные поля** каждой записи: `CreatedAt`, `CreatedBy`, `ModifiedAt`, `ModifiedBy` — импорт переносит из `Created` / `Author` / `Modified` / `Editor` списков.
- **Миграции схемы:** номерованные скрипты в git (DbUp), только вперёд; удаление столбца или смена типа — только с переносом значений (правило «данные не теряются»); перед применением — бэкап; применяет конвейер отдельной ролью, не идентичность приложения.
- Отпадают: **эталон** (`ProjectState`), **папки**, общий список отзывов.

## 5. Права, вход и безопасность

### 5.1 Вход в API (SPFx → Functions)

- Регистрация **«PPM API»**: `api://<client-id>`, область `access_as_user`, токены **v2** (`accessTokenAcceptedVersion = 2`), роли приложения (PMO, администратор PPM).
- Пакет SPFx: `webApiPermissionRequests` на «PPM API» → администратор утверждает в центре администрирования SharePoint → «Доступ к API» (клиент — «SharePoint Online Client Extensibility Web Application Principal»).
- Functions — встроенная аутентификация: «требовать вход», ответ **401** (без перенаправления), издатель v2 нашего клиента (`login.microsoftonline.com/<tenant>/v2.0`), разрешённая аудитория «PPM API», разрешённое клиентское приложение. В коде — проверка `scp` / `roles`: токен ещё не означает право.
- **CORS:** разрешить `https://smarthrua.sharepoint.com` (позже — источники Teams); предварительные запросы `OPTIONS` не должны упираться в 401 — проверяется на прототипе (этап 0).

### 5.2 Права на данные

- API перед каждым чтением и записью проверяет `ProjectAccess` и роль; правила — векторы `tests/cases/acl.json`.
- **Вторая линия — Row-Level Security** в SQL: в каждом запросе API в той же транзакции сначала `sp_set_session_context('user', …, read_only = 1)`; предикат без контекста — **ноль строк**; идентичность приложения — не `db_owner` (только чтение / запись / выполнение). Тест: «нет контекста — пусто», «чужой проект — 403». Если окажется дорого — оставляем только проверку в API (решение 13.7).
- Оргструктура: таймер **каждые 15 минут** (как сейчас) читает из Graph руководителей и пересчитывает `ProjectAccess`; раз в неделю — полный пересчёт.

### 5.3 Доступ к странице

Страница Portal остаётся на SharePoint: чтобы её открыть, человек должен быть участником сайта. Сейчас синхронизация добавляет в «Учасники сайту» всех, у кого есть права на проект. Решение (13.8): либо **таймер API добавляет людей в группу сайта** (как сейчас, только добавляет), либо группа «все сотрудники» — посетители сайта.

### 5.4 Без секретов, Graph, сеть

- Functions → SQL, Storage, Graph — управляемая идентичность; SQL — только вход Entra; секретов в настройках нет. Подключение к SQL из Node — `mssql`/`tedious` с токеном управляемой идентичности (кэш ~1 ч).
- Graph: `User.Read.All` (приложение) — руководители, подчинённые, должности, поиск людей; назначается **командой PowerShell** (`New-MgServicePrincipalAppRoleAssignment`) администратором ролей — не «галочкой» в портале.
- Сеть: базовая — брандмауэр SQL «службы Azure» + Entra-only; усиленная — частные точки доступа и VNet (плата, раздел 10). Power BI Desktop с рабочих мест — отдельное правило брандмауэра или шлюз.

### 5.5 Ключевые поля и конкурентная запись

- Инвариант «ключевые показатели — только через погоджений отчёт» обеспечивает база: роль приложения не может менять ключевые столбцы `Project` напрямую — только процедура погодження (права на столбцы или процедура + запрет обновления). Тест: прямое изменение — отказ.
- Вместо ETag списков — `rowversion`: API отдаёт версию, форма присылает её обратно; изменилось — **409 «конфлікт»** (как сейчас «412»). Проверки «свежие данные + guard» перед записью — в API. Метки прочитанного — слияние (`mergeMarks`) на сервере, без повторных попыток клиента.

### 5.6 Teams (блок 4)

В Teams работает то же приложение SPFx (вкладка / личное приложение — уже в манифесте); `AadHttpClient` работает так же. Нужно: CORS для источников Teams, проверка в клиентах Teams (браузер, рабочий стол, телефон). Если позже будет отдельное приложение Teams (не SPFx) — предавторизация его клиентов в «PPM API».

## 6. Поиск людей и выбор пользователей

Сейчас `searchPeople` — выбор людей SharePoint, `ensureUser` — номер пользователя сайта (формы проекта, риска, призначення). Станет: `GET /people?q=` по таблице `Person` (быстро; таймер держит в ней активных сотрудников из Graph), запасной путь — Graph `$search`. `ensureUser` исчезает; идентификатор человека — e-mail / object id вместо номера пользователя сайта. **Интерфейс слоя данных меняется** в этих местах — формы правятся, тесты компонентов — тоже.

## 7. Миграция

### 7.1 Этап 0 — прототип «от начала до конца» (2 дня)

До любых затрат: пустая Function App + база (бесплатная) + регистрация «PPM API» → одна функция «кто я и мои проекты» → вызов из SPFx через `AadHttpClient` на тестовом сайте, проверка CORS, токенов v2, 401, управляемой идентичности к SQL и Graph. Если что-то не взлетает — решаем до основной работы.

### 7.2 Инфраструктура и конвейер

- Bicep: группа ресурсов, SQL server + database (хранение бэкапов **GRS** явно), Function App + Storage (вход по идентичности), Application Insights + Log Analytics, оповещения, бюджет; параметры на окружение (тест / прод) — вместо `config/environments.json`, секретов нет.
- GitHub Actions: вход в Azure по OIDC (федеративные учётные данные, без секретов), `what-if` перед применением инфраструктуры, сборка `packages/ppm-logic` + API + SPFx, тесты, публикация Functions, миграции схемы. Прод — только с ручным подтверждением.
- Вынос `logic/` в `packages/ppm-logic` — первая задача этапа 1 (риск: сборка SPFx / Heft; проверяем сразу).

### 7.3 Реестр покрытия (сверка до нуля)

Обязательный отдельный проход: каждый раздел синхронизации, каждый скрипт и каждый метод `SpRepo` → где реализовано, каким тестом проверено. Цель — 0 непокрытых.

### 7.4 Перенос данных (тест)

1. **Опись потребителей** списков: Power BI, Excel / Power Query, Power Automate, представления, оповещения SharePoint — что переключить на SQL.
2. **Таблица соответствия полей** для каждого списка, включая системные (`Id`, `Created`, `Author`, `Modified`, `Editor`), вложения отзывов (→ Storage + `FeedbackFile`), людей (по e-mail; уволенные — запись `Person` без входа, ссылки не рвутся).
3. **Номера сохраняются точно:** `SET IDENTITY_INSERT ON`, затем сдвиг счётчика за максимум. Инвариант: номера проектов (PRJ-xxx), отчётов, рисков, **журнала и комментариев** — те же; на них ссылаются `kcItem`, ключи прочитанного «j<номер>» / «c<номер>» и метки `nsReadId` / `nsReadCmId` — переносятся как есть.
4. **Условие начала:** последний прогон синхронизации; `sync-dryrun` — 0 отложенного; `pmEditLog` у всех проектов пуст (правки карточки уже в журнале).
5. **Сверка до нуля:** по каждому списку — число записей и контрольные суммы полей; по каждому проекту — отчёты, риски, журнал, команда, комментарии; права — сравнение «кто что видит» до и после (`Export-ItemAcl` против `ProjectAccess`). Повторяем, пока расхождений нет.
6. **Теневой период** (вариант A — обязательно; B — по желанию): несколько дней синхронизация работает как сейчас, а API в фоне вычисляет те же результаты (права, архив, сповіщення); скрипт сравнения показывает расхождения.
7. **Переключение:** объявленное окно (≈1 час); синхронизация — пауза; финальная выгрузка и сверка; переключатель окружения → API; чек-лист; синхронизация в Azure Automation — отключить (не удалять).
8. **Откат:** переключатель обратно на `SpRepo`; изменения, записанные в SQL после переключения, — скриптом в списки **вместе с эталоном** (`Sync-ProjectStateFromCard`) и флагами применения (`srApplied`, `apApplied`, `paApplied`) — иначе синхронизация после включения откатит ключевые поля или повторит события. Откат репетируем на тесте.
9. **Списки SharePoint** после переключения — архив только для чтения; **не удаляются** (правило «данные не теряются»).

### 7.5 Прод

- B: прод `/sites/ppm` создаётся сразу с API: пустая база, приложение, роли.
- A: сценарий 7.4 на проде, окно обслуживания вне рабочего времени, заранее — письмо пользователям.
- Любой вариант: ворота 2 — отдельное «да».

## 8. Тестирование и наблюдение

- Векторы `tests/cases/*.json` — на коде API (Jest), как у приложения; новые правила — новыми векторами; прототип (`prototypeForm.test.ts`) продолжает проходить.
- Тесты API: контракт с `ApiRepo`, права (чужой проект — 403, без контекста RLS — пусто), транзакции (погодження целиком или никак), конкурентная запись (два PMO решают один отчёт → один успех, второй — 409), даты «только дата».
- **Оповещения** (группа действий — вам): таймер не отработал два интервала подряд (вместо письма о сбое задания Automation), рост 5xx, нагрузка и место SQL, пауза тестовой базы, сбой экспорта бэкапа, бюджет.
- Документация: SPEC, DATA-MODEL, ARCHITECTURE, DEPLOYMENT (процедуры восстановления), CHANGELOG — отдельной задачей в каждом этапе.

## 11. Резервное копирование и восстановление

**Цели:** обычные сбои и ошибки — потеря не больше **10 минут**, восстановление до **2 часов**; авария региона — потеря до **1 часа**, восстановление — **несколько часов** (без геореплики; с ней — минуты, решение 13.5).

| Что | Как | Хранение |
|---|---|---|
| База — на любой момент | встроенные бэкапы Azure SQL (журнал каждые 5–10 мин), восстановление на момент времени | прод — 35 дней (максимум) |
| База — долгосрочно | Long-Term Retention | еженедельно 12 недель, ежемесячно 12 месяцев, ежегодно 5 лет |
| Авария региона | хранение бэкапов GRS (задаём явно в Bicep) → гео-восстановление | автоматически |
| Логическая копия, независимая от сервера | **основной путь — CSV ключевых таблиц** таймером Functions раз в сутки; **еженедельно BACPAC** — согласованная копия (`CREATE DATABASE … AS COPY OF`) → экспорт через ARM API (идентичность: участник SQL + запись в Blob; ожидание завершения, оповещение при сбое) → копия удаляется | контейнер в другом регионе с политикой неизменяемости по времени (90 дней) + мягкое удаление; политику проверяем на записи экспорта |
| Скриншоты отзывов | Blob: версии + мягкое удаление 30 дней | |
| Код, схема, инфраструктура | git + Bicep: окружение поднимается заново | бессрочно |
| Защита от удаления | блокировка «CanNotDelete» на группе ресурсов прода (снимается только для осознанных изменений инфраструктуры); удаление логического сервера SQL уничтожает его бэкапы на момент времени — поэтому LTR и внешний экспорт обязательны | |

**Процедуры** (в `docs/DEPLOYMENT.md`): восстановление на момент времени, из LTR, гео-восстановление, из BACPAC и из CSV; **учение раз в квартал** — копия в `rg-ppm-restore`, сверка, фактическое время.

**SharePoint:** после переезда — только страница и пакет приложения (версии в git); списки — архив только для чтения.

## 13. Решения, нужные до старта

1. Порядок: **B** (Azure на тесте → прод сразу на Azure) или **A** (прод сейчас, переезд потом) — раздел 2; для B — подтверждение, что на тесте нет рабочих данных.
2. Уровень SQL для прода: Standard S0–S1 (рекомендую) или serverless.
3. Сеть: базовая или частные точки доступа (+ плата).
4. Бэкапы: 35 дней / LTR 12 недель · 12 месяцев · 5 лет / внешняя копия 90 дней — подходят?
5. Геореплика (горячий резерв в другом регионе) — или достаточно гео-восстановления (потеря до 1 ч, восстановление — часы).
6. **Согласование с ИБ** (ворота): данные PPM в Azure SQL (Германия), вне политик хранения Microsoft 365; журналы — там же.
7. RLS как вторая линия защиты — делаем (рекомендую) или только проверки в API.
8. Доступ к странице: таймер добавляет людей в «Учасники сайту» (как сейчас) или «все сотрудники — посетители».
9. Кто из администраторов выдаёт согласия (раздел 12) и когда.
