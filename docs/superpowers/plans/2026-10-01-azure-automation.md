# Перенос синхронизации с Mac в Azure Automation — план

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** синхронизация портала (`Invoke-PMOSync.ps1`) работает по расписанию в Azure Automation, не зависит от Mac; Mac-расписание снято.

**Architecture:** учётная запись Azure Automation с системной управляемой учётной записью (Managed Identity); runbook PowerShell 7.4 = `PMO.Common.ps1` + `Invoke-PMOSync.ps1`, собранные в один файл; доступ — SharePoint Sites.Selected (FullControl только на сайты портала) и Graph User.Read.All; **блокировка — служебная строка в «Еталон показників» с проверкой версии (If-Match), одна для Mac и Azure**; кэш оргструктуры — зашифрованная переменная Automation; 4 часовых расписания со сдвигом 15 минут + еженедельный пересчёт прав. (Правки по кросс-ревью Sonnet 01.10 — помечены «ревью».)

**Tech Stack:** Azure Automation (runtime PowerShell 7.4), PnP.PowerShell 3, Az.Accounts / Az.Automation / Az.Resources (локально, для настройки), Microsoft Graph.

## Исходные данные (проверено 01.10.2026)

- Подписка **PMO Automation** `0c1bf98e-6c99-47ce-a61c-fa4fec2c22df`, роль пользователя — Владелец, состояние «Активный».
- Каталог подписки — тот же тенант, что SharePoint: `faa553e4-cc39-45f2-8dc6-ce0ae64d968b` (`smarthrua.onmicrosoft.com` / `eclectic.group`). Управляемая учётная запись Automation может работать с SharePoint и Graph этого тенанта напрямую.
- Поставщик `Microsoft.Automation` не зарегистрирован (регистрируется при создании учётной записи).
- `Invoke-PMOSync.ps1` уже поддерживает `-ManagedIdentity` (`Connect-PnPOnline -ManagedIdentity`), Graph — через `Invoke-PnPGraphMethod`.
- Mac-расписание (`Set-MacSchedule.ps1 -AllDay`): каждые 15 минут; воскресенье 3:00 — `-RebuildPermissions`. Напоминания (`-SendReminders`) ещё не включены.
- Синхронизация на тесте: ~28 с на запуск; полный пересчёт — ~160 с.

## Global Constraints

- Прод (`/sites/pmo`) — только после отдельного «да»; этот план — тест, прод — тем же runbook после создания прод-сайта.
- Создание платных ресурсов Azure и выдача прав в Entra ID — только после «да» пользователя; входы в Azure / Entra выполняет пользователь (браузер или код устройства), пароли агент не вводит.
- Права — минимальные: Sites.Selected (FullControl только на сайт портала), Graph User.Read.All; Mail.Send — только когда включим напоминания, с ограничением одним ящиком (ApplicationAccessPolicy, см. DEPLOYMENT).
- Mac и Azure не синхронизируют один сайт одновременно в рабочем режиме (конфликт версий) — на время проверки Azure работает в `-DryRun`.
- Одна версия кода: runbook собирается из `scripts/` последнего коммита; в репозитории — скрипт сборки и проверка, что собранный runbook совпадает с исходниками.
- Стоимость: 96 запусков/сутки × 30–70 с (с холодным стартом) ≈ 1 500–3 400 мин/мес; 500 мин бесплатно, остальное по $0,002/мин ≈ **$2–6/мес**; правило оповещения — центы. Хранилище и Log Analytics не используются.

## Решения (нужно подтверждение пользователя)

1. **Регион:** рекомендую **Poland Central** (ближе всего); альтернатива — West Europe.
2. **Вход:** рекомендую **системную управляемую учётную запись** — нет сертификата и пароля, нечего продлевать и хранить. Альтернатива — сертификат существующего приложения «PMO Sync» в «Сертификатах» Automation (тогда раз в год продлевать).
3. **Кто выдаёт права:** назначение прав управляемой учётной записи (Graph User.Read.All, SharePoint Sites.Selected) требует роли глобального администратора или администратора привилегированных ролей. Если у пользователя её нет — команды выполняет администратор тенанта.
4. **Часы работы:** как сейчас — круглосуточно каждые 15 минут (стоимость та же, $2–6 в месяц) или только 6:00–22:00 (runbook выходит сразу вне окна; экономия незначительна). Рекомендую круглосуточно.
5. **Оповещение о сбоях:** письмо при неуспешном задании (Azure Monitor, бесплатно для 1 правила-оповещения в разумных пределах) — рекомендую да.

### Этап 0: Подготовка на Mac

- [x] Установить модули Az локально (официальные модули Microsoft из PowerShell Gallery): `Install-Module Az.Accounts, Az.Resources, Az.Automation -Scope CurrentUser` — только для настройки; синхронизация их не использует.
- [ ] Вход в Azure выполняет пользователь: `Connect-AzAccount -Tenant faa553e4-… -Subscription 0c1bf98e-… -UseDeviceAuthentication` (код вводится в браузере, где уже выполнен вход).
- Критерий: `Get-AzContext` показывает подписку PMO Automation.

Порядок: этап 1 (код) и этап 3 (права) можно вести параллельно, но проверочный runbook этапа 3 требует модуля из этапа 2.

### Этап 1: Код — runbook-совместимая синхронизация

**Files:** `scripts/Invoke-PMOSync.ps1`, `scripts/PMO.Common.ps1`, новый `scripts/Build-Runbook.ps1`, `runbooks/` (собранный файл), `tests/Test-Scripts.ps1`.

- [x] **Блокировка в SharePoint (ревью: переменные Automation не атомарны, файл в песочнице не живёт, сейчас снимается только при нормальном завершении).** Служебная строка «Еталон показників» `psProject = 0` (JSON: кто, когда, до какого времени); захват — чтение с ETag и запись с `If-Match` (412 — занято другим запуском, выход); срок — 45 мин (дольше любого запуска); снятие — в `finally` вокруг всего тела синхронизации. Один механизм для Mac и Azure — на время перехода они не могут синхронизировать сайт одновременно. `-DryRun` блокировку не берёт (только чтение), но проверяет, свободна ли. Векторы — `Test-LockPlan` (чистая функция: свободно / занято / просрочено).
- [x] **Кэш оргструктуры:** на Mac — файл `~/.pmo-sync/managers-<env>.json` (как сейчас); в Automation — **зашифрованная** переменная `pmo-managers-<env>` (персональные данные; лимит 512 КБ, сейчас ~2 КБ). Выбор — по наличию `Get-AutomationVariable` (не по ОС). Переменная создаётся на этапе 2; если её нет — работа без кэша с предупреждением.
- [x] **Время по Киеву (ревью):** песочница Automation в UTC — дата в `pmLastComment` (сейчас `ToLocalTime()`) и граница напоминаний (`(Get-Date).Date`) — через `ConvertTo-Kyiv` (`FindSystemTimeZoneById` 'Europe/Kyiv' → 'Europe/Kiev' → 'FLE Standard Time').
- [x] **Частичный сбой = ошибка задания (ревью):** счётчик `$stats.errors` для сбоев записи (права не выданы, запись не перенесена, эталон не записан); в конце при `errors > 0` — `throw` (задание «Failed» → оповещение). Предупреждения правил (не PM, подделка) ошибками не считаются.
- [x] **Сборка runbook:** `Build-Runbook.ps1` — `#Requires`, справка и `param()` синхронизации сверху, затем содержимое `PMO.Common.ps1` на месте строки `. (Join-Path $PSScriptRoot …)`, затем остальное → `runbooks/Invoke-PMOSync.ps1`; заголовок «собрано из коммита <hash>» (+ «изменения не закоммичены», если рабочая копия грязная). `Test-Scripts.ps1`: в собранном файле нет `$PSScriptRoot`, синтаксис разбирается, файл совпадает со сборкой из текущих исходников.
- [x] **Публикация:** `scripts/Publish-Runbook.ps1` (Az.Automation): `Import-AzAutomationRunbook -Type PowerShell72 … -Published -Force` (тип для среды 7.4 — уточнить на этапе 4), проверка заголовка-коммита опубликованной версии; запускает человек после входа в Azure.
- [x] **Параметры runbook:** `-SiteUrl`, `-ManagedIdentity`, `-RebuildPermissions`, `-DryRun`, `-Env` (для имён переменных). Вывод — тот же журнал (`Write-Host` → поток вывода задания).
- [x] Тесты: блокировка и кэш (файловый вариант) — на Mac как раньше; абстракция с подменой команд Automation — векторы в `Test-Scripts.ps1`.
- Критерий: `Test-Scripts.ps1` зелёный, Mac-синхронизация работает как раньше (`sync-dryrun`, `sync`).

### Этап 2: Ресурсы Azure (после «да»)

- [ ] Группа ресурсов `rg-pmo-automation` (регион из решения 1).
- [ ] Учётная запись Automation `aa-pmo-sync`, системная управляемая учётная запись включена.
- [ ] Среда выполнения (Runtime environment, новая модель) PowerShell 7.4 с пакетом **PnP.PowerShell 3.x** (версия как на Mac; нужен PowerShell ≥ 7.4.4 / .NET 8). Импорт ~100 МБ может занять 10–30 мин.
- [ ] **Шлюз (ревью):** модуль импортирован («Доступно») и пустой runbook в этой среде выполняет `Import-Module PnP.PowerShell; Get-Module PnP.PowerShell`. Не прошёл — план Б: другая версия PnP.PowerShell 3.x или Hybrid Worker; дальше не идём.
- [ ] Зашифрованная переменная `pmo-managers-test` (пустая строка).
- [ ] Управляемой учётной записи **не выдаются роли Azure** (ни в подписке, ни в группе ресурсов) — ей нужен только доступ к SharePoint и Graph.
- Критерий: учётная запись «Готово», шлюз модуля пройден.

### Этап 3: Права управляемой учётной записи (выполняет администратор тенанта)

- [ ] Graph **User.Read.All** (application) — назначение роли приложения сервисному субъекту управляемой учётной записи (`New-MgServicePrincipalAppRoleAssignment` или PnP `Add-PnPEntraIDServicePrincipalAppRole`).
- [ ] SharePoint **Sites.Selected** (application) — то же (назначение роли сервисному субъекту управляемой УЗ — только PowerShell/Graph, не портал); затем **FullControl на `/sites/pmo-test`**: `Grant-PnPEntraIDAppSitePermission -AppId <appId сервисного субъекта, не objectId> -DisplayName aa-pmo-sync -Site <url> -Permissions FullControl` — выполняет пользователь входом в приложение PMO Deploy (делегированное AllSites.FullControl, роль администратора SharePoint или владельца сайта).
- [ ] Проверочный runbook `PMO-WhoAmI` — **реальные операции синхронизации (ревью)**: вход `-ManagedIdentity`; чтение проектов; `Get-PnPGroupMember` (PMO-адміністратори, владельцы); `Get-PnPRoleDefinition`; `siteusers` с фильтром приложений (видна ли сама управляемая УЗ); Graph `users/<owner>/manager` через `Invoke-PnPGraphMethod` (запасной вариант — токен `Get-AzAccessToken`); на служебном списке «Перевірка форматів»: `Add-PnPFolder`, разрыв наследования и назначение роли записи, перенос записи в папку, `SystemUpdate`; блокировка: захват и снятие служебной строки; запись и чтение переменной кэша.
- Критерий: всё успешно; на другой сайт тенанта доступа нет (проверка отказом).

### Этап 4: Runbook и пробные запуски

- [ ] Импорт `runbooks/Invoke-PMOSync.ps1` как runbook `PMO-Sync` (PowerShell 7.4, среда из этапа 2), публикация.
- [ ] Ручной запуск `-DryRun -ManagedIdentity -SiteUrl <test> -Env test`; сравнить вывод с Mac `sync-dryrun` (те же предупреждения и счётчики). Время запуска — в таблицу метрик.
- [ ] Ручной запуск `-RebuildPermissions -DryRun` — время.
- [ ] Журнал: вывод `Write-Host` (поток Information) виден в выводе задания; если нет — включить запись подробных сообщений в настройках runbook.
- Критерий: вывод совпадает с Mac по смыслу; время запуска ≤ 60 с (холодный старт Automation добавляет 20–40 с — норма).

### Этап 5: Расписания

- [ ] 4 расписания «каждый час» с началом в :00, :15, :30, :45 → `PMO-Sync` (`-ManagedIdentity -SiteUrl <test> -Env test -DryRun` на время проверки).
- [ ] Еженедельно, воскресенье 3:00 (Europe/Kyiv) → `-RebuildPermissions`.
- [ ] Часовой пояс расписаний — Europe/Kyiv (переход на летнее время).
- [ ] (Решение 5) правило оповещения по метрике `TotalJob` (Status = Failed, без рабочей области Log Analytics) → письмо владельцу. Хранение журналов заданий — 30 дней (по умолчанию Automation).
- [ ] Сутки параллельно: Mac — рабочий режим, Azure — `-DryRun`; сверка: у Azure 0 ошибок, те же предупреждения. Общая блокировка в SharePoint исключает одновременную запись (DryRun только читает).
- Критерий: ≥ 90 пробных запусков за сутки без ошибок.

### Этап 6: Переключение

- [ ] Снять Mac-расписание: `Set-MacSchedule.ps1 -Env test -Remove`.
- [ ] Убрать `-DryRun` из расписаний Azure; первый рабочий запуск — вручную, проверить журнал и приложение.
- [ ] Сутки наблюдения: ошибки заданий, время запуска, сценарии (смена PM → права через ≤ 15 мин; погодження → карточка).
- Критерий: сутки без ошибок; изменения на сайте применяются как с Mac.
- Откат: вернуть Mac-расписание (`Set-MacSchedule.ps1 -Env test -AllDay`) и отключить расписания Azure.
