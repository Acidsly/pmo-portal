# Этап 4 — доступ в карточке, Teams, синхронизация, прод

> Ход работ: план на согласовании (2026-09-25), кросс-ревью проведено, замечания учтены.

**Цель:** закончить приложение до выпуска: раздел «Доступ до картки» как в прототипе, работа в Teams, боевая синхронизация на `pmo-test`, выпуск на `/sites/pmo`.

**Спецификация:** [docs/SPEC.md](../../SPEC.md), [проектное решение](../specs/2026-09-24-spfx-portal-design.md). Прототип: `accessList` (строки 1267–1276), раздел в карточке (строка 1333), тексты `accessTitle`, `accessDesc`, `lvlEdit`, `lvlRead`, `lvlFull`, `pmoGroup`.

## Ограничения

- Приложение не пишет права и `pmoAcl`; список доступа пишет только синхронизация (она знает цепочки руководителей из Entra ID). Graph из браузера не используется.
- Внутренние имена не переименовываются; новое поле — через `F`, идемпотентно.
- Регистрация приложения синхронизации — действие человека (вход администратора в Chrome).
- Каталог приложений тенанта, Teams и прод — только после отдельного «да» в чате.

## Задачи

### Задача 1. Синхронизация пишет список доступа

**Файлы:** `scripts/Deploy-PMO.ps1`, `scripts/Invoke-PMOSync.ps1`, `tests/cases/access.json` (новый), `tests/Test-Scripts.ps1`.

- Поле `pmAccess` (Note, Hidden, простой текст — до 63 999 символов в списке) в «Проєкти»: «Службове: доступ». Предел — 200 человек (~30 000 символов); сверх — обрезка с флагом `"more": N`, приложение пишет «і ще N».
- В синхронизации функция `AccessList($item)` строит упорядоченный список по правилам прототипа: PM (edit, роль `pm`) → цепочка PM (edit, `mgr`) → власник (edit, `owner`) → стейкхолдери (read, `stake`) → цепочки власника и стейкхолдеров (read, `mgr`); без повторов (первое вхождение побеждает). Элемент: `{ "e": email, "n": имя, "j": должность, "l": "edit"|"read", "r": роль }`. Считается в том же проходе, что и ACL (цикл по проектам в `Invoke-PMOSync.ps1`, кэш цепочек `Get-Chain` уже прогрет), — одно место истины и без лишних запросов к Graph. У архивного проекта синхронизация пишет всем `read` — так же, как выдаёт права.
- JSON пишется `SystemUpdate` только при изменении (сравнение строки), в `-DryRun` — только вывод.
- Общие векторы `tests/cases/access.json`: участники + цепочки руководителей → ожидаемый список. Проверяет `Test-Scripts.ps1` (функция из AST, как `CalcRag`).

**Приёмка:** векторы проходят; `sync-dryrun` на `pmo-test` показывает, что `pmAccess` будет записан у всех проектов.

### Задача 2. Раздел «Доступ до картки» в приложении

**Файлы:** `data/map.ts` (+`pmAccess` в `PROJECT_SELECT`), `data/types.ts`, `logic/access.ts` (новый: разбор JSON, устойчивый к пустому и битому значению), `panels/ProjectCard.tsx`, `i18n/strings.ts`, `spfx/test/access.test.ts`.

- Последний раздел карточки, как в прототипе: заголовок, пояснение `accessDesc`, строки «аватар · имя · роль/должность · уровень», в конце — «Група «PMO — адміністратори» · повний доступ».
- Пусто (синхронизация ещё не прошла) → пояснение «Список з'явиться після синхронізації» и строка PMO.
- Проект в архиве — уровни «перегляд» для всех, кроме PMO. Приложение применяет это и само (как наложение отчётов в `overlay.ts`): отчёт «Завершено» уже виден на экране, а синхронизация ещё не переписала `pmAccess`. Это не дублирование по ошибке — вектор «архив, а в JSON ещё edit» в `tests/cases/access.json`.

**Приёмка:** Jest на разбор и архив; в Chrome на `pmo-test` раздел совпадает с прототипом.

### Задача 3. Адрес портала в Teams

**Файлы:** `PmoPortalWebPart.ts` (интерфейс свойств `{ siteUrl?: string }` вместо `{}`), `PmoPortalWebPart.manifest.json` (`preconfiguredEntries.properties.siteUrl`), `scripts/Deploy-App.ps1` — тип и значение по умолчанию меняются вместе.

- В Teams (личное приложение) `pageContext.web` — не сайт портала. Свойство веб-части `siteUrl`: на странице SharePoint всегда текущий сайт; в Teams — значение из `preconfiguredEntries`, которое `Deploy-App.ps1` подставляет при сборке пакета для окружения.
- Ссылки приложения (Loop, открыть в SharePoint) — от адреса портала.
- Тема Teams (default / dark / contrast) → светлая / тёмная тема приложения, если пользователь не выбрал свою.

**Приёмка:** в локальной отладке с подменённым адресом данные грузятся с сайта портала; пакет содержит адрес окружения. Боевая проверка запроса `SPHttpClient` из Teams к другому семейству сайтов — в задаче 5.

### Задача 4. Регистрация и первая боевая синхронизация на `pmo-test`

Действия человека и проверка, без кода (кроме найденных ошибок):
1. Пользователь: `Register-PMOApps.ps1 -Stage Sync … -DeviceLogin` (вход в Chrome), пароль сертификата — в «Связку ключей».
2. `sync-dryrun` → разбор вывода вместе с пользователем → `sync`.
3. Проверка в Chrome: отчёты применены (`srApplied`), карточки обновлены, журнал заполнен (включая «Редагування картки» из `pmEditLog`), права выданы (вход тестовым пользователем без участия — проект не виден), архивный проект — только чтение, «Доступ до картки» заполнен.

**Приёмка:** сценарии 1–9 из `docs/SPEC.md` §12 на `pmo-test`.

### Задача 5. Пакет Teams

**Файлы:** `scripts/Deploy-App.ps1` (действие для каталога тенанта), `docs/DEPLOYMENT.md`.

- Личное приложение Teams из того же пакета (`supportedHosts` уже есть), иконки `spfx/teams/`. Публикация: `Add-PnPApp -Scope Tenant` в каталог тенанта → `Sync-PnPAppToTeams` (права администратора тенанта). Только после «да».
- Каталог тенанта — одна версия пакета на тенант, поэтому Teams указывает на прод `/sites/pmo`; тестовый сайт остаётся на каталоге сайта.

**Приёмка:** приложение видно в Teams у пользователя, открывает прод-данные с его правами (запросы к `/sites/pmo` из контекста Teams проходят, запись отчёта работает).

### Задача 6. Выпуск на прод

- `Deploy-App.ps1` сейчас принимает только тестовый сайт (проверка `-test` в начале, «Этап 1»). Снять её для прода с тем же воротами, что у `Invoke-Env.ps1`: прод только с `-ConfirmProduction`.


Только после отдельного «да»: `-Env prod -Action sync-dryrun` → `deploy -ConfirmProduction` → `app` → регистрация PMO Sync для `/sites/pmo` → `sync` → расписание (Azure Automation или планировщик — по выбору пользователя) → задача 5.
