## Источник событий

Ничего нового ради сповіщень в журнал не пишется.
- **Журнал «Зміни показників»** (строки одного действия — одно событие, как `toEvents`) и **Коментарі**.
- Новизна — по номеру записи (`Id`, индексирован всегда): метки «прочитано до» / «разослано до» — номера, не время.
- **Номер события** = наибольший `Id` его строк. **Граница публикации** — наибольший номер журнала / комментариев, который синхронизация обработала в конце раздела 7; хранится в служебной строке «Еталон показників» (`psProject = 0`, поле `psNotifyEdge`). Приложение показывает в колокольчике только события до границы — событие, записанное синхронизацией наполовину, не превращается в два.
- **Служебные записи журнала** (Seed, Refresh, Renumber, миграции Deploy) — не события: эти скрипты после своих записей сдвигают границу и метки всех строк «Прочитане» (общая функция в `PMO.Common.ps1`, как `Sync-ProjectStateFromCard`); вектор «запись служебного скрипта — 0 писем».

## Классификация и получатели (чистые функции, векторы `tests/cases/notify.json`)

**`Get-NotifyKind` / `notifyKind`** — вид события из строк: `created`, `assigned`, `submitted`, `decided` (Погоджено / Повернуто / авто-повернення), `applied` (статус, стан, %, дати, витрати), `archived` (строка `pmStatus` → «Завершено» / «Скасовано», прежнее «Архівний»; в том же событии — и содержимое отчёта), `risk`, `cardEdit`, `comment`.

**`Get-NotifyRecipients` / `notifyRecipients`** — вход: вид и строки события; проект **сейчас** (PM, власник, команда, статус, `pmAccess`); риск по `kcItem` сейчас (оценка, власник; удалён — оценка из строк события, иначе — как < 15); автор (`kcChangedBy`, у комментария — Author; пусто — автор никто).

| Вид | PM | Власник | Команда | Власник ризику | PMO |
|---|---|---|---|---|---|
| created, assigned | ✓ | ✓ | ✓ | — | — |
| submitted | — | — | — | — | ✓ |
| decided, applied | ✓ | ✓ | ✓ | — | — |
| archived | ✓ | ✓ | ✓ | — | ✓ |
| risk | ✓ | оцінка ≥ 15 | оцінка ≥ 15 | ✓ (если есть доступ) | — |
| cardEdit | ✓ | ✓ | — | — | — |
| comment | ✓ | ✓ | ✓ | — | — |

- PMO получает **только** `submitted` и `archived` по всем проектам; остальное — только как PM / власник / команда.
- Получатель должен сейчас иметь доступ (`pmAccess`). **Исключение — `assigned`:** колишній PM / власник (из `kcFrom`) получает **письмо** об этом событии — без деталей проекта и без ссылки на карточку; в колокольчике у него этого события нет (журнал проекта ему уже не виден) — расхождение задокументировано.
- Архивный проект: после события `archived` — ничего (комментариев в архиве нет; неразосланные до архивации — уходят, если они раньше `archived`).
- Автор своё событие не получает; пустой автор (действия синхронизации) — получают все по правилу.

| `nsTeamsId` | Number | синхронизация | разослано в ленту активности Teams до |

- **Права:** список — без доступа участникам; строку создаёт синхронизация **сразу со всеми метками** (одной записью) и даёт права **только этому человеку** на новом уровне **«Оновлення (портал)»** (просмотр и правка элемента, без добавления и удаления; создаётся в Deploy по образцу «Додавання (портал)»). Чужих строк не видит, свою не удалит.
- **Недоверие к меткам:** синхронизация зажимает `nsRead*` и `nsMailed*` в 0…последний номер; дубль строки или строка без человека — предупреждение, не сбой.
- **Лимиты:** строк — по числу людей с доступом (десятки — сотни; порог 5 000 не грозит); уникальные права — по строке на человека (предел 50 000, рекомендация до 5 000); запись — только при «прочитано» и смене настроек; приложение читает свою строку по `nsUser` (индекс); синхронизация — все строки одним запросом.
- Скрыт (раздел 8a), поля — `F`, значения `nsMode` — в Deploy, `values.ts`, `VAL`, синхронизации одинаково.
- **CLAUDE.md:** исключение из правила «приложение SPFx не пишет…» — только свои `nsReadId`, `nsReadCmId`, `nsMode`, `nsLang` в «Прочитане».

## Синхронизация — раздел 7 «Сповіщення» (последним, после раздела 5 «Права»)

**Выключатель:** рассылка — только с ключом `-SendNotifications -NotifyFrom <ящик>`; на тесте ещё `-NotifyOnlyTo <e-mail через запятую>` — письма остальным не уходят (в журнал запуска — «пропущено: не в списке»). Без ключа раздел только ведёт строки «Прочитане», метки и границу.

1. **Строки людей.** Каждый из `pmAccess` любого проекта и из группы PMO — строка (если нет), все метки = текущий последний номер, `nsDigestAt` = сегодня — первый запуск и новый человек не получают старого. Человека добавили в уже идущий проект: старые события проекта ему не рассылаются — письма «одразу» берут только события новее границы прошлого запуска, а потолок давности 24 часа ограничивает повторы.
2. **Новые события** — журнал и комментарии с номером > границы прошлого запуска (фильтр `Id gt`), сгруппированные; плюс события, не разосланные из-за сбоя, — не старше **24 часов** (потолок давности).
3. **«Одразу»:** каждому — его события с номером > `nsMailedId`, не старше 24 часов, по правилу получателей; есть — одно письмо. Метка `nsMailedId` сдвигается **у всех строк каждый запуск**: у кого письмо ушло — после отправки; кому не положено (режим, правило, нет доступа) — сразу. Включил письма после «Вимкнено» — старое не придёт.
4. **«Щодня»:** первый запуск после 08:00 по Киеву (`ConvertTo-Kyiv`), если `nsDigestAt` < сегодня (по Киеву): события за **вчера по Киеву** (по номеру: от первого номера вчерашнего дня до последнего; первый номер дня — граница, которую раздел 7 запоминает в первом запуске после полуночи), **кроме уже разосланных «одразу»** этому человеку (режим по умолчанию не дублирует); в понедельник — за пятницу, субботу и воскресенье одной сводкой; пусто — письма нет, `nsDigestAt` = сегодня.
5. **Письмо:** тема «PPM: що змінилося — N подій» / «PPM: підсумок за дд.мм»; по проектам — событие (вид, «було → стало», кто, причина или текст комментария до 300 символов); ссылка — `#projects/all/<ID>` (карточка; адрес по `logic/route.ts`), для отчёта / риска — форма `rep:<n>` / `risk:<n>`; подвал — «Налаштувати сповіщення»; HTML-экранирование; язык — `nsLang`.
6. **Отправка:** Graph `users/<NotifyFrom>/sendMail`, письмо — одному получателю; пауза ~2 с между письмами, не больше 40 писем за запуск (остаток — в следующем запуске, метки это позволяют); `Update-SyncLock` каждые 10 писем; ограничение по времени раздела (5 минут).
7. **Ошибки:** 429 / 5xx — метка не сдвигается, повтор в следующий запуск (в пределах 24 часов); 4xx адресата (нет ящика, отключён) и человек без e-mail — предупреждение, метка сдвигается, запуск не падает.
8. **DryRun** — «кому, сколько событий», ничего не отправляет и не пишет (строки «Прочитане» тоже не создаёт).
9. В конце — граница публикации `psNotifyEdge`.

## Приложение

- **Колокольчик** (рядом с «?»): красная точка, если есть события с номером > `nsReadId` / `nsReadCmId` и ≤ границы, по правилу получателей для меня. Запрос — журнал `Id gt <метка>` и `kcDate` за последние 14 дней (индексы), комментарии — уже загружены; обновление — вместе с данными (возврат на вкладку, раз в 5 минут).
- **Панель «Сповіщення»:** новые сверху по проектам, ниже — прочитанные за 14 дней бледнее; нажатие открывает запись. **Открыли панель — показанное отмечено прочитанным** (своя строка: `nsReadId` = номер последнего показанного события), точка исчезает; новые подсвечены, пока панель открыта.
- **Налаштування** в панели: режим писем, язык писем.
- Строки ещё нет — без точки, подсказка «Сповіщення з'являться протягом 15 хвилин».
- Запись строки — со свежей версией (`If-Match`), метка только растёт (`max`).
- `SpRepo.stamp` — список «Прочитане» в отметке изменений; `Export-ItemAcl.ps1`, `Show-Person.ps1` — новый список.
- **Прототип:** колокольчик, точка, панель, настройки — по тем же правилам, в памяти страницы.
- Переводы uk / en / ru.

## Лента активности Teams

- **Приложение PPM в Teams** — пакет Teams для нашего SPFx-приложения (личная вкладка, манифест 1.7+ — свой `teams/manifest.json` в пакете SPFx) с `webApplicationInfo` (приложение Entra, которое отправляет уведомления) и типом активности `ppmEvents` («PPM: {count} нові події»); установка пользователям — политикой Teams (вы).
- **Отправка** — синхронизация, раздел 7, вместе с письмами: Graph `POST /users/{id}/teamwork/sendActivityNotification`, одно уведомление на человека за запуск (`chainId` — одно и то же в течение дня: новое заменяет старое, лента не засоряется); `previewText` — «3 нові події: PRJ-002, PRJ-005» (до 150 символов); лимит Teams — 20 уведомлений в минуту на человека, у нас — одно за запуск.
- **Переход:** `topic.webUrl` — глубокая ссылка на личную вкладку PPM с `subEntityId=notifications`; приложение в Teams читает его из контекста Teams и открывает панель «Сповіщення» (маршрут формы `notifications`, он же — по ссылке из письма «Налаштувати сповіщення»).
- **Метки:** своя метка `nsTeamsId` в строке «Прочитане» (разослано в Teams до), те же правила получателей, потолок давности и выключатель (`-SendTeams`, на тесте — тот же `-NotifyOnlyTo`). Режим «Вимкнено» выключает и Teams.
- **Ошибки:** 403 «Teams app is not installed» — приложение не установлено человеку: предупреждение один раз в сутки, метка сдвигается, письмо и колокольчик работают как обычно.
- **Неизвестное (проверяется первым шагом этапа):** может ли отправлять уведомления управляемая учётная запись Azure (её ID в `webApplicationInfo`) или нужна регистрация приложения «PMO Sync» с сертификатом в Azure Automation; разрешение — `TeamsActivity.Send` (приложение, согласие администратора) или RSC `TeamsActivity.Send.User` в манифесте; работает ли свой манифест Teams с SPFx 1.23 при установке из каталога приложений сайта.

## Что делает пользователь

- Сообщает адрес ящика-отправителя.
- Даёт синхронизации в Azure разрешение Graph `Mail.Send` и ограничивает его в Exchange только этим ящиком (по моей инструкции).
- Решает, когда включить рассылку для фокус-группы (после проверки на себе).
- Teams: загружает пакет приложения PPM в центр администрирования Teams, политикой устанавливает его фокус-группе; даёт разрешение на отправку уведомлений (по итогам проверки первым шагом этапа 6).

## Риски

1. Активный проект — письмо каждые 15 минут в рабочее время; есть режим «Лише щодня»; при жалобах — «не чаще раза в час».
2. `Mail.Send` без ограничения ящиком действует на все ящики тенанта — ограничение обязательно.
3. «Прочитано до» — без отметки отдельных событий (решение: колокольчик с точкой).
4. Дубль письма при сбое между отправкой и записью метки — редко, лучше потери.
5. Колишній PM получает письмо о смене, но не видит его в колокольчике.
6. Ограничение 40 писем за запуск: утренняя сводка для сотен людей растянется на несколько запусков (до часа).
