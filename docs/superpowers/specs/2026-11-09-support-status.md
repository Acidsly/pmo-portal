## 1. Запрос и как я его понимаю

Запрос владельца (дословно): «Є запит додати окремий статус до проєкта — підтримка, куди переносити проєкти, які не завершені, а потребують постійного нагляду (помилки, обслуговування, інше). Там контроль буде по ресурсах які виділяються на цей проєкт, по бюджету та строках вручну — так само як й по звичайним проєктам але винести їх в окрему вкладку Підтримка та в окрему аналітику на головній. В подальшому по бюджету контролювати в рамках виділених годин кожного ресурса на проєкті підтримки та по завданням які будуть підключені по строках. Статус звіти будуть подаватись не 2 рази на тиждень, а один раз на тиждень.»

Что из этого следует:

| # | Требование | Сейчас | Нужно |
|---|---|---|---|
| T1 | Состояние «Підтримка» для проекта, который не завершён, но требует постоянного надзора | 6 фаз: Ініціація, Планування, Реалізація, Призупинено, Завершено, Скасовано | новое значение / признак |
| T2 | Контроль ресурсов, бюджета, сроков — вручную, как у обычных проектов | статус-отчёт: оценки терміни / бюджет / ресурси, ключевые показатели, погодження PMO | то же самое, без новой механики |
| T3 | Отдельная вкладка «Підтримка» | вкладки: Головна, Проєкти, Статус-звіти, Ризики, Архів, Відгуки | новая вкладка по образцу «Архів» / «Проєкти» |
| T4 | Отдельная аналитика на главной | одна аналитика по всем активным | разделить портфель проектов и підтримку |
| T5 | Статус-отчёт для підтримки — раз в неделю | свежесть: ≤ 8 дн. зелёный, 9–14 жёлтый, > 14 красный (SPEC правило 7) | своя норма свежести для підтримки |
| T6 | Позже: бюджет — в рамках выделенных часов каждого ресурса; сроки — по подключённым задачам | нет часов, нет задач (R8 «Інтеграція з хелпдеском» — далёкая перспектива) | заложить, но не делать сейчас |

### Неоднозначности (вопросы — в разделе 8)

1. **Частота отчётов (главное).** «не 2 рази на тиждень, а один раз на тиждень» не совпадает с тем, что заложено в портале: сейчас норма — **раз в неделю** (зелёный до 8 дней — неделя + день запаса; жёлтый — пропущен один отчёт; красный — больше двух недель). Возможные прочтения:
   - (а) у обычных проектов на практике PMO просит отчёт 2 раза в неделю, а портал «мягче» практики; для підтримки — неделя, т. е. текущая норма портала подходит підтримці как есть, а для обычных проектов можно ужесточить (зелёный ≤ 4 дня);
   - (б) оговорка, имелось в виду «не раз на тиждень, а раз на 2 тижні» — підтримка отчитывается реже обычных проектов (зелёный ≤ 15, жёлтый 16–21, красный > 21 — или ≤ 14 / 15–28 / > 28);
   - (в) обе категории — раз в неделю, ничего не меняется.
   Рекомендация: сделать норму свежести **параметром категории** (одна функция, общие векторы) — тогда любое прочтение — это смена чисел, а не кода. Числа — решение владельца.
2. **Переход в «Підтримка» и обратно** — только статус-отчётом с причиной и погодженням PMO (как любая смена фазы, правило 6a), или PMO одной кнопкой? Рекомендация — отчётом: механика уже есть (причина, журнал, эталон, погодження), исключение из правила «ключевые показатели только отчётом» не нужно.
3. **Из какой фазы.** Рекомендация: из любой активной (обычно Реалізація → Підтримка после запуска), обратно — в любую активную (например, крупная доработка → Реалізація), выход — Завершено / Скасовано → архив. Новый проект PMO может сразу создать в «Підтримка» (системы, которые уже в эксплуатации).
4. **Підтримка — фаза или категория.** Если «Підтримка» — фаза, проект на підтримці не может быть «Призупинено» (пауза підтримки = смена фазы на Призупинено и выпадение из вкладки). Если категория — фаза живёт отдельно. См. варианты в разделе 3.
5. **Входит ли підтримка в «Проєкти» и общий портфель.** Рекомендация: вкладка «Проєкти» и аналитика проектов — **без** підтримки (иначе нет смысла выносить); «Статус-звіти», «Ризики», «Мої проєкти», колокольчик, журнал, поиск — по всем, с фильтром «Підтримка».
6. **Кто погоджує отчёты підтримки** — PMO, как сейчас (рекомендация), или владелец проекта / отдельная роль.
7. **Бюджет підтримки** — на какой период: на год / договор (`pmBudget` = бюджет на период підтримки, `pmPlanEnd` = конец периода) — рекомендация; или помесячный лимит (нужна новая механика — отложить до часов, раздел 6).
8. **«Стратегічний» для підтримки** — допустим ли (влияет на вариант «Тип = Підтримка»).

## 3. Варианты архитектуры

### A. Новая фаза `pmStatus = «Підтримка»` — **рекомендую**

Поле уже называется «Фаза проєкту» (жизненный цикл), а підтримка — естественная фаза после запуска: Ініціація → Планування → Реалізація → **Підтримка** → Завершено.

- **Плюсы:** ровно то, что просит владелец («окремий статус»); вся механика уже есть — смена через отчёт с причиной, погодження PMO, журнал, эталон, права (активный проект — PM правит), архивирование; новых полей и миграций нет; минимальные изменения синхронизации.
- **Минусы:** нельзя быть одновременно «на підтримці» и «призупинено» (пауза = выход из вкладки); значение нужно добавить во все списки фаз (реестр раздела 2, сверка покрытия); любое место, где сегодня `isActive`, нужно осознанно решить — включать підтримку или нет (главная, «Проєкти», «Запуски», «Зсуви»).
- **Защита от расползания:** ни одного сравнения со строкой «Підтримка» вне `isSupport` / `Test-SupportStatus` (Test-Scripts и Jest проверяют поиском по коду, как сейчас для имён переменных). Тогда переход к C в будущем — замена одной функции.
- **Оценка:** 5–7 сессий Claude (см. раздел 7).

### B. Новый тип `pmType = «Підтримка»` (рядом с Стратегічний / Звичайний)

- **Плюсы:** фаза остаётся независимой (на підтримці можно «Призупинено»); тип уже ключевой показатель, меняется отчётом с причиной.
- **Минусы:** тип сейчас — флаг стратегичности (иконка щита, представления «Стратегічні», сортировка, `srProjectType` / `riProjectType` копии, CAML `$order` по `pmType`): проект підтримки не сможет быть стратегическим, а смысл поля размывается; правок не меньше, чем в A, плюс копии типа в отчётах и рисках; владелец просит «статус», не тип.
- **Оценка:** 6–8 сессий. Не рекомендую.

### C. Отдельный признак «Режим» (`pmMode`: Проєкт / Підтримка) — ключевое поле

Новое поле в «Проєкти» (`pmMode`, Choice, по умолчанию «Проєкт») и в отчёте (`srMode`), ключевое поле эталона (`Get-StateKeys`), переносит синхронизация (`TARGET_FIELD`), журнал.

- **Плюсы:** чистая модель — фаза, стратегичность и режим независимы; удобнее для будущего (часы и задачи хелпдеска привязываются к режиму, а не к фазе); пауза на підтримці возможна.
- **Минусы:** самый дорогой: новые поля в двух списках, эталон (`tests/cases/state.json`), перенос и журнал в синхронизации (runbook), форма отчёта (новое поле + причина), AI-контекст; два понятия вместо одного — PM должен понимать разницу между «Фаза» и «Режим».
- **Оценка:** 8–11 сессий.

## 5. Частота отчётов — правило по дням подачи

Решение 09.11: **поточні проєкти — понедельник и четверг, підтримка — четверг.** Текущее правило «зелёный ≤ 8 дней, жёлтый ≤ 14, красный > 14» считает отчёт раз в 1–2 недели нормой — практике оно не соответствует, его заменяем.

### Правило

- **День подачи** (`slot`): для поточних — каждый понедельник и четверг, для підтримки — каждый четверг. Таблица дней — в одном месте (`REPORT_DAYS = { project: [1, 4], support: [4] }`), та же — в `PMO.Common.ps1`.
- **Пропущенный день подачи** — день подачи строго раньше сегодняшнего, после которого нет отчёта: `missed = число дней подачи S, где lastReport < S < today`. В сам день подачи он ещё не пропущен (до конца дня).
- **Свежесть:** `missed = 0` — зелёный; `1` — жёлтый (пропущен один отчёт); `≥ 2` — красный; отчётов нет — серый. Для поточних: отчёт в понедельник → зелёный до четверга включительно, в пятницу — жёлтый, со вторника — красный. Для підтримки: отчёт в четверг → зелёный до следующего четверга включительно, в пятницу — жёлтый, через неделю — красный.
- Отчёт, поданный в другой день (вторник после пропущенного понедельника), закрывает все пропуски до своей даты — снова зелёный.
- **Категория — по текущей фазе.** Переход в підтримку сам является отчётом, так что в момент перехода проект зелёный.
- **Какой отчёт считать** (решение 09.11): **только погоджений** — `pmLastUpdate`, как сейчас. В расчёт идёт дата подання (`srDate`), поэтому отчёт, поданный в понедельник и погоджений в среду, закрывает понедельник. Пока отчёт на погодженні, проект может временно стать жёлтым; это видно в колонке «Звіт» по пометке «на погодженні» (`RepMark`). Отдельной логики для этого не делаем. В подсказке свежести показываем «звіт від <дата> на погодженні», если такой есть.
- Праздники и отпуск не учитываются (как сейчас); при необходимости — позже.

### Где меняется (реестр по ревью)
