# Бэклог R9–R12: варианты реализации

Дата: 29.10.2026. Статус: **варианты на выбор владельца**, код не начат. Кросс-ревью (Sonnet) 29.10.2026 — замечания учтены. Берём по одной задаче после выпуска текущих изменений (1.7.6 / 1.7.7, гости); на каждую выбранную — план в `docs/superpowers/plans/` и ревью плана до кода (`.claude/rules/workflow.md`).

Сроки — «Claude делает код, тесты, документацию; человек — решения, приёмка на тесте». Сессия ≈ один рабочий заход.

Общее для всех четырёх:
- приложение не пишет ключевые поля, журнал и права — только синхронизация; новые действия PMO идут **заявкой в служебный список**, который переносит синхронизация (образец — «Призначення», раздел 0c `Invoke-PMOSync.ps1`, `Get-AssignmentPlan` + векторы `tests/cases/assignments.json`);
- правило, которое есть и в синхронизации, и в приложении, — общие векторы `tests/cases/*.json`;
- в каждой задаче: прототип → приложение; `docs/SPEC.md`, `docs/DEPLOYMENT.md`, «Довідка» uk / en / ru, выпуск в `docs/RELEASES.*`; правка `Invoke-PMOSync.ps1` → `Build-Runbook.ps1` и `Publish-Runbook.ps1 -Env test`; `tests/Test-Scripts.ps1` и Jest;
- новые поля, списки и значения выбора — только добавляются (`F`, `Ensure-List`, расширение `Choices`), повторный deploy без дублей.

Рекомендуемый порядок: **R11 → R12 → R9 → R10** (R11 — без изменений синхронизации; R12 меняет модель прав архива; R10 самый большой).

## R12. Вернуть проект из архива — кнопка только для PMO

**Что есть.** Архив = «Завершено» / «Скасовано» (`Test-ArchivedStatus`, `isArch`). Попадает туда только погоджений статус-отчёт; синхронизация ставит `pmArchivedAt` (и `pmActualEnd`), все права становятся «чтение» (`Get-Access … archived`, `Get-FolderRole` — `read` для всех списков), отчёты «на погодженні» возвращаются (0b), права архива замораживаются (`Test-ArchiveFrozen`, отметка `arch2:`).

**Откуда «прежний статус».** Последняя строка журнала `kcField = pmStatus` с переходом в архивный статус — её «было». Нет строки — PMO выбирает сам. Общей функцией с векторами `tests/cases/unarchive.json`.

**Что меняется в любом варианте (по ревью):**
- **права PMO на заявку в архивном проекте.** Сейчас PMO на папке «Призначення» архивного проекта — только чтение (`Get-GroupFolderRole`), а приложение пишет только в папку проекта. Нужно «добавление» PMO в эту папку и у архива → смена модели отметки прав (`v3:` / `arch3:`) либо `rebuild-permissions` для всех архивных проектов; векторы `acl.json`;
- **блокировки архива** снимаются только для этой заявки: `guard.ts` (`gArchived` срабатывает раньше `assign`), `AssignForm.tsx` (`archivedNote`), `assignmentPlan` / `applyAssignments` и `Get-AssignmentPlan` (векторы `assignments.json` в обе стороны);
- **поля при возврате:** `pmStatus` → выбранный, `pmArchivedAt` и `pmActualEnd` очищаются (что с `pmProgress` — решение); эталон до карточки, откат при сбое — как в 0c;
- **в том же запуске** 0c обновляет в памяти `pmStatus` / `pmArchivedAt` — иначе 0b, раздел 0 и права (раздел 5) увидят «архив». Отметку `arch2:` сбрасывать не нужно: после смены статуса проект не «заморожен», отметка станет `v2:` сама;
- **журнал и колокольчик:** новый вид `kcKind` «Повернення з архіву» (значение выбора добавляется в `Deploy-PMO.ps1`), новый `notifyKind` `restored` — иначе вид «Призначення» даст `assigned`; переводы в `values.ts` и `VAL` прототипа;
- **кнопка** — в карточке архивного проекта (страница «Архів»), видна PMO и владельцам.

### Вариант A — поле `paStatus` в «Призначення» (рекомендую)
Новое необязательное поле «Повернути зі статусом». Форма: статус (по умолчанию прежний), причина обязательна; при желании в той же записи — новый PM / власник. Синхронизация: в 0c архивный проект принимается только с `paStatus`.
- плюсы: готовые гарантии #43 (кто может, причина, эталон до карточки, откат, одна необработанная заявка на проект);
- минусы: «Призначення» становится общей заявкой PMO, правило `Get-AssignmentPlan` усложняется.
- объём: 3–4 сессии.

### Вариант B — отдельный список «Повернення з архіву»
`Lists/ProjectRestore`: `rsProject`, `rsStatus`, `rsNote`, `rsApplied`; свой раздел синхронизации, папки, права, чтение в приложении.
- плюсы: чистая модель; минусы: тот же код второй раз. Объём: 4–5 сессий.

### Вариант C — возврат через статус-отчёт
PMO подаёт «отчёт» и сам его погоджує — путает роли, архив блокирует подачу. Не рекомендую.

**Решения владельца:**
1. Исключение из «ключевые поля — только через отчёт» для статуса при возврате из архива — согласны? (рекомендую: да, только PMO, только с причиной, в журнал.)
2. Статус по умолчанию — прежний из журнала, PMO может поменять? Или строго прежний?
3. `pmActualEnd` и `pmProgress` при возврате: очистить / оставить?
4. Можно ли в той же заявке сменить PM / власника? Обязан ли PM сразу подать отчёт?
5. Колокольчик «Проєкт повернено з архіву» — PM, власнику, команді? (рекомендую: да.)

## R11. Передача проектов от одного PM другому

**Что есть.** Смена PM одного проекта — «Змінити PM / власника / країну» (#43): запись в «Призначення» в папке проекта, синхронизация переносит, отчёт прежнего PM «на погодженні» возвращается автоматически, права (раздел 5) — новому PM, колокольчик — `assigned`.

### Вариант A — массовая форма поверх «Призначення» (рекомендую)
Кнопка PMO «Передати проєкти» (страница «Проєкти», режим PMO): «від кого» → его активные проекты с галочками (по умолчанию все) → «кому» → причина. Приложение создаёт **по одной записи «Призначення» на проект** (в папке проекта, причина копируется в каждую). Синхронизация не меняется.
- чистая функция `transferPlan`: что передаётся, что пропускается (архив, уже у нового PM, есть необработанное «Призначення» — `gAssignPending`);
- перед каждой записью — свежая проверка `SpRepo.fresh` + `guard('assign')` по проекту, а не список из экрана; записи — последовательно (ограничения SharePoint на частоту запросов);
- итог: «передано N, пропущено M (почему)», повтор только для непереданных.
- плюсы: ноль новой логики в синхронизации, все гарантии #43; минусы: нет одной «атомарной» передачи. Объём: 2 сессии.

### Вариант B — одна заявка «передача» на сервере
`Lists/PmTransfers` (от кого, кому, проекты / «все», причина); синхронизация раскрывает в изменения.
- плюсы: одна запись, история передач в одном месте; минусы: новый список и раздел синхронизации, «все» на момент запуска ≠ на момент заявки, дублирует #43. Объём: 3–4 сессии.

**Решения владельца:**
1. Только PM, или вместе с владельцем / страной? (рекомендую: только PM.)
2. Проекты в «Призупинено» — передаются вместе с активными? (рекомендую: да, всё не архивное.)
3. Новому PM — сповіщення по каждому проекту (уже работает) или одно сводное? (рекомендую: по проекту.)

## R9. Комментарии к отзывам со скриншотами и файлами — все участники сайта

**Что есть.** «Відгуки» — на тесте и на проде (`-Feedback`, решение 20.10.2026). `Lists/Feedback`: каждый видит свои (`ReadSecurity` «свои»), скриншоты — вложения; статус и ответ `fbAnswer` ставят владельцы. Синхронизация копирует текст, статус, ответ в `Lists/FeedbackPublic` (видят все, `fpId` индексирован). Колокольчик автора — «Відгук розглянуто» (`fpDecidedAt`).

Ограничение: вложения самих отзывов участникам не видны, поэтому комментарий с файлами нельзя держать в `Lists/Feedback`.

### Вариант A — список «Коментарі до відгуків» (рекомендую)
`Lists/FeedbackComments`: `fcFeedback` (номер отзыва = `fpId`, индексированное число), `fcText`, вложения. Приложение показывает только комментарии к существующим отзывам (номер берётся из открытого отзыва, чужой номер — отбрасывается при чтении).
- права: участники — читать всё и **добавлять**, без правки и удаления (данные не теряются, вложения не пропадают); владельцы — всё;
- приложение: в `FeedbackView` лента комментариев, текст, вставка скриншота (`logic/image.ts`), файлы; `fbAnswer` остаётся «официальным ответом»; `WritableList` в `SpRepo.ts` расширяется;
- колокольчик: новый вид `fbComment` (ключ `fc<номер>`) — автору отзыва, прежним комментаторам и владельцам; правило — векторы `tests/cases/notify.json`;
- синхронизация не нужна (по желанию — счётчик комментариев в `FeedbackPublic`).
- плюсы: просто, права штатные; минусы: всё приложенное видят все участники. Объём: 3 сессии.

### Вариант B — библиотека файлов с папкой на отзыв
Большие файлы и предпросмотр Office, но две сущности на комментарий и права папок — избыточно.

### Вариант C — открыть сами отзывы всем
Меняет решение «свои отзывы видит автор» (личные скриншоты). Не рекомендую.

**Решения владельца:**
1. Комментировать любой отзыв может любой участник? (запрос — «всі учасники»; рекомендую так.)
2. Свой комментарий можно править / удалять? (рекомендую: нет — только добавлять; ошибочный убирает владелец.)
3. Файлы: типы (картинки, PDF, Office) и размер (например, до 10 МБ, до 5 файлов).
4. Кому колокольчик о новом комментарии: автор отзыва, комментаторы, владельцы — все трое?

## R10. Замены PM на время отсутствия — отдельный справочник

**Что мешает.** «PM» — одно поле `pmManager`, и на нём держится:
- права «Редагування (портал)» — только PM (`Get-Access`, раздел 5; «первое вхождение побеждает» — заместитель, который уже читатель, остался бы «read»);
- приложение: `guard.ts` — правки только если я PM (`gPmChanged`), погодити можно только отчёт текущего PM (`gNotPmAuthor`); `cardFields` / `Fresh`; `isPm` в представлениях;
- синхронизация: отчёт применяется, только если автор = PM (`Get-ApplyAction`); автовозврат «Змінився PM» (`Get-PendingReturns`) вернул бы отчёт заместителя; напоминания PM (раздел 6) — только `pmManager`;
- колокольчик «PM» — по `pmManager` (`notify.ts`); «Доступ до картки» (`pmAccess`) — нет роли «заступник».

Значит, замена — это **вторая роль с правами PM** на срок, а не ещё один читатель.

Справочник (во всех вариантах): `Lists/PmDeputies` — `pdManager`, `pdDeputy`, `pdFrom`, `pdTo` (даты включительно, по Киеву — `ConvertTo-Kyiv`), `pdReason` (выбор: Відпустка / Лікарняний / Відрядження / Інше) + `pdNote`, `pdProjects` (пусто — все проекты PM), служебное `pdState`.

### Вариант A — временный «соредактор» (рекомендую как цель)
`pmManager` не меняется. Синхронизация на каждом запуске считает действующие замены (`Get-DeputyPlan`, векторы `tests/cases/deputies.json`: границы дат по Киеву, начало / конец внутри 15 минут, заместитель удалён из Entra ID, заместитель = сам PM, PM сменён во время замены, перекрывающиеся замены). Заместитель получает «edit» как PM (роль `deputy` в `Get-Access` — выше «read»), пишется в скрытое `pmDeputy` и `pmAccess`. «PM или действующий заместитель» — во всех местах из списка выше, в обеих частях (векторы `acl.json`, `reports.json`, guard); отчёт заместителя в журнале — «подано заступником». Конец срока — права снимает тот же пересчёт.
- плюсы: проект остаётся за PM, история честная, ничего не надо «возвращать»;
- минусы: самая большая правка правил; права по расписанию — до 15 минут задержки.
- объём: 6–8 сессий.

### Вариант B — временная смена PM через «Призначення»
На `pdFrom` — «Призначення» PM → заместитель, на `pdTo` — обратно. Отчёт PM «на погодженні» возвращается при каждой смене, журнал засоряется, PM при передаче проекта во время отпуска получает его обратно. Не рекомендую.

### Вариант C — только справочник и уведомления (без прав)
Справочник, бейдж «PM відсутній до …, заступник …» в карточке и списке, сповіщення; правка — по-прежнему PM (или PMO через #43).
- плюсы: 2–3 сессии, права не трогаем; первый шаг к A; минусы: заместитель не может подать отчёт.

Поэтапно: **C, затем A**.

**Сповіщення:** «Вас призначено заступником PM <ім'я> з … по … (причина)» — заместителю; «Заміна почалась / закінчилась» — заместителю и PM; PMO — новая замена. Виды `deputySet` / `deputyStart` / `deputyEnd` в `notify.ts` + векторы; роль «Заступник PM» — переводы, «Доступ до картки», «Довідка».

**Решения владельца:**
1. Вариант: A, C или C → A?
2. Кто ведёт справочник: только PMO, или PM сам вносит свои отсутствия (PMO видит и исправляет)?
3. Замена на все проекты PM или по проектам (разные заместители)?
4. Отчёт заместителя — от его имени, погоджується как обычно, с пометкой «подано заступником»?
5. Причина — выбор + комментарий или свободный текст?
6. Напоминания PM во время замены — заместителю, PM или обоим?
7. PM сменён (#43 / R11) во время замены — замена прекращается?
