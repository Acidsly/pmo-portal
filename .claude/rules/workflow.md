# Как вести изменение (SDD) и проверять результат

Дополняет «Порядок работы над изменением» в CLAUDE.md: что делать до кода и как доказать, что сделано.

## Спецификация до кода

Масштаб определяет глубину:

| Сложность | Признаки | Что делать |
|---|---|---|
| Простая | одна правка, очевидная реализация | сразу ветка → тест → правка |
| Средняя | несколько файлов, синхронизация + приложение | уточнить требования → план в `docs/superpowers/plans/` → ревью плана → одобрение пользователя → реализация по этапам |
| Сложная | новые поля / списки, права, миграции, Azure | то же + 2–3 варианта архитектуры на выбор пользователю |

- Для средней и сложной — **не писать код без одобренного пользователем плана**. План: постановка, выбранный подход, этапы-чеклист (`- [ ] Этап N: что + файлы + критерии приёмки`), порядок выкладки (deploy / app / runbook).
- Неоднозначность — один вопрос с вариантами ответа и рекомендацией, затем ждать ответа.
- Инструменты: плагин superpowers (`brainstorming`, `writing-plans`, `executing-plans`, `test-driven-development`, `systematic-debugging`, `verification-before-completion`) — включается настройками проекта.

## Сроки в планах

Оценки — из расчёта «Claude — основной исполнитель (код, тесты, документация, сборка), человек помогает (тенант, согласия, приёмка)»: колонка «Кто», срок нашей работы (дни / сессии) и отдельно календарное ожидание (согласия, пилот).

## Ошибка → тест

Найдена ошибка (ревью, своя проверка, пользователь) — сначала тест, который ловит **класс** ошибки, и доказательство: без исправления он падает, с исправлением проходит. В итоге честно сказать, какие найденные ошибки покрыты тестом, а какие нет.

- Состояние формы — в чистых функциях `spfx/src/webparts/pmoPortal/logic/`, не в компоненте.
- Правило, которое есть и в синхронизации, и в приложении, — общие векторы `tests/cases/*.json`; поведение формы прототипа и приложения — векторы, которые гоняет и Jest, и `spfx/test/prototypeForm.test.ts` на прототипе в jsdom.

## Сборка перед коммитом приложения

`tsc --noEmit` пропускает то, что валит сборку SPFx (`@typescript-eslint/no-use-before-define`: компонент использован выше объявления, обработчики, которые снимают друг друга). Перед коммитом кода `spfx/` — `scripts/spfx.sh npm run build`; взаимно ссылающиеся обработчики объявляй через `let` заранее.

## Сверка покрытия (reconciliation loop)

Когда есть набор входов и правила, которые должны покрыть их все (значения выбора в прототипе / `Deploy-PMO.ps1` / CAML / `values.ts` / синхронизации; поля эталона; разделы «Довідки» на трёх языках; миграции): отдельным проходом после кода составить таблицу «вход → где обработан», найти непокрытые и конфликтные, исправить, повторить до «N/N, 0 расхождений». Сверять по фактическому содержимому, не по именам. Приёмку на реальных данных делает человек.

## Кросс-ревью

Основная работа — Opus. После плана средней+ задачи и после кода — независимое ревью агентом на Sonnet (`Agent`, `model: "sonnet"`): находки с severity и вердикт. Найденное — исправить (с тестом) или явно согласовать с пользователем как долг.
